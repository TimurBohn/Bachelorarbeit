\section{Verilog}
    Verilog ist neben SystemVerilog und VHDL die am weitesten verbreitete Hardwarebeschreibungssprache.
    Hardwarebeschreibungssprachen definieren u.a. den Aufbau von Schaltungen auf dem Register-Transfer-Level (RTL) und stellen somit die Grundlage für die Hardwarekonfiguration dar.
    Es werden Signale unterschiedlicher Typen (oft \verb|wire| (\("\)Leitung\("\)) und \verb|reg| (\("\)Register\("\))) genutzt sowie deren Verhalten beschrieben.
    Hierbei werden oft if-else-, oder always-Blöcke in Verbindung mit Taktgebern genutzt, um das Hardwareverhalten wie gewünscht zu konfigurieren.
    Ein wichtiger Aspekt ist hierbei, dass die Reihenfolge im Code i.d.R. keinen Rückschluss darüber zulässt, was zuerst ausgeführt wird.
    Stattdessen wird Hardware beschrieben, die parallel arbeitet.
    Nachfolgend ist ein Beispiel für einfachen Verilog-Code angegeben, in dem einige der genannten Konstrukte genutzt werden:

    \begin{minted}[breaklines, fontsize=\small]{verilog}
        module LED(
                input wire clk,
                input wire switch,
                input wire[3:0] counter,
                input wire button,
                output wire[3:0] out4Bit,
                output reg [7:0] out8Bit
            );
            assign out4Bit = (switch) ? counter : 4'b0;
            always @(posedge clk) begin
                if (switch) begin
                    if (button)
                        out8Bit <= 8'b10101010;
                    else
                        out8Bit <= 8'b01010101;
                end
            end
        endmodule
    \end{minted}
    \captionof{listing}[Einfaches Verilog-Beispiel LED.v]{Verilog-Beispiel LED.v, welches genutzt wurde, um die Funktionalität des Boards zu testen.}
    \label{lst:LED.v}


    In dem Beispiel trägt das Modul den Namen der Datei.
    In dieser Moduldefinition werden die Input- sowie Output-Signale (\verb|wire| und \verb|reg|) festgelegt.
    In der separaten Constraint-Datei wird für die Input- und Output-Signale jeweils angegeben, welches Bauteil der Peripherie es abbildet.
    So wird \verb|clk| als 100MHz-Taktgeber definiert, \verb|switch| und \verb|counter| werden auf Schalter, \verb|button| auf einen Button und \verb|out4Bit| sowie \verb|out8Bit| auf LEDs gemappt (vergleiche \cref{fig:basys3}).
    Der globale Schalter \verb|switch| steuert beide Output-Leitungen auf jeweils verschiedene Weise.
    Bei \verb|out4Bit| werden die LEDs durch ihre darunterliegenden Schalter ein- und ausgeschaltet, sofern der globale Schalter eingeschaltet ist.
    Ist dieser ausgeschaltet, leuchten die LEDs nicht.
    Dies wird durch den \verb|assign|-Ausdruck beschrieben, wobei der ternäre Operator genutzt wird, um abzufragen, ob \verb|switch| ein- oder ausgeschaltet ist.
    Ist der globale Schalter an, werden die Werte der Schalter \verb|counter| durchgereicht, ansonsten enthält \verb|out4Bit| vier Nullen (\verb|4'b0|: \("\)4 Bit, 0 binär\("\)).
    Der 8-Bit-Ausgang hingegen verwendet den \verb|switch| auf eine andere Art.
    \verb|out8Bit| nutzt zunächst den Taktgeber mit einem \verb|always|-Block.
    Dieser gibt an, dass zu jeder steigenden Flanke (\verb|posedge|) des Taktgebers/der Clock (\verb|clk|) zunächst mit einem \verb|if|-Block geprüft wird, ob der globale Schalter umgelegt ist.
    Nur wenn \verb|switch| eingeschaltet ist, lässt sich das 8-Bit-Register verändern, sonst behält es seinen vorherigen Wert bei.
    Ist dies der Fall, kann mit dem Drücken des Buttons \verb|button| eingestellt werden, in welchem der zwei Muster die 8 LEDs, die auf \verb|out8Bit| gemappt sind, leuchten sollen.
    Wird der globale Schalter währenddessen wieder ausgeschaltet, behalten die LEDs ihr Muster bei, bis es wieder durch \verb|button| in Kombination mit \verb|switch| verändert wird.

    Hier wird auch deutlich, dass die Reihenfolge im Code keinen Rückschluss über die Ausführungsreihenfolge geben kann.
    Werden die Schalter von \verb|counter| umgelegt, nachdem der Button \verb|button| gedrückt wurde, ändern sich die LEDs dennoch, obwohl sie im Code weiter vorne stehen.
    Auch ist bei RTL-Code eine echt parallele Ausführung möglich.
    Im Gegensatz zu klassischen Programmiersprachen, bei denen eine Abfolge von Befehlen beschrieben wird, beschreibt RTL-Code eine Hardwarekonfiguration.
    Dadurch, dass oft distinkte Bereiche des FPGA genutzt werden, arbeiten diese Bereiche unabhängig und tatsächlich parallel voneinander, wobei in klassischen Programmiersprachen teilweise der Anschein einer Parallelität durch schnelle Wechsel erweckt wird.
    In unserem Beispiel würde dies bedeuten, dass beim zeitgleichen Drücken des Buttons und Umlegen eines Schalters, beide Schaltungsteile parallel reagieren.

\section{FPGAs}
    Field Programmable Gate Arrays, oder FPGAs sind beliebig konfigurierbare Hardwareschaltungen.
    Im Gegensatz zu Microcontrollern oder CPUs, bei denen mit festgelegten Instruktionen gearbeitet und Software geschrieben wird, die mit diesen vorgegebenen \("\)Werkzeugen\("\) eine bestimmte Funktionalität umsetzt, wird bei FPGAs die Hardware selbst entwickelt.
    Hierbei wird mit einer Hardwarebeschreibungssprache eine Schaltung konfiguriert, die einen bestimmten Zweck erfüllt und eine bessere Passung zur gewünschten Funktionalität bietet, als dies z.B. generische Microcontroller tun.
    Derselbe FPGA kann sich somit je nach Konfiguration bspw. wie eine ALU, ein digitaler Signalprozessor (DSP), eine anwendungsspezifische integrierte Schaltung (ASIC), eine ARM-CPU oder eine x86-CPU verhalten.

    Diese Flexibilität erreichen FPGAs, da sie aus mehreren frei konfigurierbaren Logikblöcken bestehen, wobei die Anzahl der Logikblöcke die Komplexität an umsetzbaren Schaltungen bestimmt.
    Je mehr Logikblöcke, desto komplexere Schaltungen können mit einem FPGA umgesetzt werden.
    Ein solcher Logikblock enthält Input/Output-Elemente zur Kommunikation (bspw. LEDs, UART, interne Signale), Switching/Routing-Blöcke zur Verbindung der Bauteile sowie sogenannte Konfiguraitons-Logikblöcke.
    Diese Konfigurations-Logikblöcke generieren aus einem Input-, einem Clock- und einem Resetsignal einen Output durch die Verwendung von Lookup-Tables, Flipflops und Multiplexern.
    Durch diese Bestandteile wird dann das gewünschte Verhalten modelliert.
    Lookup-Tables oder LUTs sind Bauteile, die aus mehreren Eingangssignalen ein Ausgangssignal generieren.
    Hierbei funktionieren sie wie Wahrheitstabellen für boolesche Ausdrücke.
    Es muss lediglich für jede Kombination an Eingangssignalen das Ausgangssignal in den Speicher geschrieben werden.
    Beispielsweise würde an die Adresse 3 einer 3-Input LUT der Wert (0 oder 1) geschrieben werden, der ausgegeben werden soll, wenn am Eingangssignal A eine 0 und an B und C eine 1 anliegen.
    Die Adressierung erfolgt hierbei im Binärsystem, da ABC = 011\textsubscript{2} = 3\textsubscript{10}.
    Analog dazu ist jede Adresse eines LUT, bspw. 0-7 bei einer 3-Input LUT, eine mögliche Kombination an Eingangssignalen.
    So kann jede logische Schaltung, die deterministisch bzw. nicht zeitabhängig ist, in LUTs abgebildet werden.
    Simple Schaltungen mit wenigen Eingängen können nur eine LUT beanspruchen, bei komplexeren Schaltungen werden mehrere LUTs miteinander verschaltet.
    Die Ausgabe einer LUT wird dann als eine der Eingaben der nächsten LUT verwendet.
    Für zeitabhängige Schaltungen werden zusätzlich Flipflops und Speicherbausteine genutzt.

    Um zu einer fertig konfigurierten Hardwareschaltung zu gelangen, wird ein Designprozess befolgt.
    Zunächst wird in einer Hardwarebeschreibungssprache Code auf dem Register-Transfer-Level (RTL) geschrieben.
    Dieser RTL-Code kann in einem Analyse- bzw. Simulationsschritt einer ersten Prüfung unterzogen werden, wo grobe Fehler auffallen sollten.
    Im Anschluss erfolgt der Syntheseschritt, in dem der RTL-Code in eine Netzliste überführt wird.
    Diese bildet ab, welche Bauteile theoretisch benötigt würden, um die Schaltung wie beschrieben umzusetzen.
    Eine Netzliste ist vergleichbar mit einem Zwischencode beim Kompilieren von Code in der Softwareentwicklung.
    Im Implementierungsschritt werden in einem sogenannten Place-and-Route-Verfahren die theoretischen Bauteile der Netzliste auf die tatsächlich auf dem FPGA vorhandenen Bauteile gemappt.
    Hier werden benötigte physische Bauteile, also Lookup-Tables, Flipflops und Multiplexer auf dem FPGA verortet und benötigte Bauteile miteinander verbunden. % Ist verortet richtig?
    Diese Informationen werden in einen Bitstream geschrieben.
    In einem letzten Schritt wird dieser Bitstream auf den FPGA übertragen.
    Dies erfolgt entweder persistent in den Flash-Speicher, sodass die Konfiguration bei Neustart des FPGA erhalten bleibt, oder flüchtig in den SRAM.
    Im Rahmen der vorliegenden Arbeit wurde der Bitstream, der die Konfiguration der Schaltung und den Benchmark enthält, im SRAM des FPGA gespeichert, war somit flüchtig und musste bei jedem Neustart des Boards erneut geladen werden.

    Somit ermöglichen FPGAs eine große Flexibilität, da sie jede erdenkliche Schaltung abbilden können und in ihren Funktionen nicht so stark eingeschränkt sind wie z.B. Microcontroller.
    Dadurch können sie auf den jeweiligen Usecase zugeschnitten werden und bieten deshalb meist eine höhere Geschwindigkeit und Energieeffizienz als Microcontroller, weisen gleichzeitig aber auch eine im Vergleich größere Komplexität auf.
    Sie unterscheiden sich untereinander hinsichtlich der Leistung/Mächtigkeit vor allem in der Anzahl der Logikblöcke, der maximalen Taktfrequenz, im Stromverbrauch, der RAM-Größe und in der Anzahl an I/O Pins.

\section{RISC-V, SERV und Servant}
    RISC-V \parencite{risc-v-website} ist eine open-source Instruction Set Architecture (ISA), die den Befehlssatz eines Prozessors festlegt.
    Somit bestimmt die ISA, welche Instruktionen von einer CPU verarbeitet werden können.
    Im Gegensatz zu anderen verbreiteten ISAs wie x86 oder ARM kann RISC-V beliebig implementiert und erweitert werden, ohne dass Lizenzkosten anfallen.
    Dadurch bietet RISC-V eine größere Flexibilität und Anpassungsfähigkeit im Rahmen der Hardwareentwicklung zur Erfüllung der gewünschten Funktionalität.
    Teile, die nicht gebraucht werden, bspw. Ganzzahlmultiplikation und -division können je nach Anwendungsfall aufgenommen oder weggelassen werden.
    Dies ermöglicht eine optimierte Nutzung verfügbarer Hardwareressourcen.
    Der folgende RISC-V Assembly-Code wurde für die Erstellung der Benchmarks genutzt, was im \cref{Bau ausführbarer Benchmarks} (\("\)SERV-Simulation und Bau ausführbarer Benchmarks\("\)) ausführlich erklärt wird.

    \begin{minted}[breaklines, fontsize=\small]{asm}
        #ifndef GPIO_BASE
        #define GPIO_BASE 0x40000000
        #endif
        .globl _start
        _start:
	        lui a0, %hi(GPIO_BASE)  /* a0 = GPIO base address*/
	        addi a0, a0, %lo(GPIO_BASE)
	        addi t0, zero, 1        /* Clear t0, t0 = Value */
        loop:
            sb t0, 0(a0)            /* Write to LEDs */
            xori t0, t0, 1          /* invert LED */
        delay:                            /* Delay loop */
            li	a4, 0x1
            li	a3, 0x1             /* a4 = a3 = i = 1 */
            li	a2, 0x3e9           /* a2 = 1001 */
        outer_loop:
            mv	a5, a4              /* n = a5 = i */
            j	check_loop_zu_Ende
        ungerade:
            slli	a1, a5, 0x1
            add	a5, a1, a5
            addi	a5, a5, 0x1     /* n = 3*n+1 */
        check_even_odd:
            andi	a1, a5, 0x1     /* n%2 == 1 ? jump ungerade : n = n/2 */
            bnez	a1, ungerade
            srai	a5, a5, 0x1
        check_loop_zu_Ende:
            bne	a5, a3, check_even_odd /* n!=1 ? weiter in Collatz : i++ */
            addi	a4, a4, 0x1
            bne	a4, a2, outer_loop     /* i != 10001 ? Collatz mit i : LED wechseln */
            j loop
    \end{minted}
    \captionof{listing}[Benchmark in RISC-V Assembly]{Finaler Benchmark in RISC-V Assembly, der in der Simulation und auf dem FPGA lief. Die daraus gebaute .hex-Datei ist im Github-Repository \parencite{GitHub-Bachelorarbeit} zu finden.}
    \label{lst:collatz.S}


    In dem Beispiel tauchen mehrere, oft genutzte RISC-V-Instruktionen auf.
    Mit \verb|lui| (load upper immediate) werden die oberen 20 Bit in ein 32-Bit-Register geladen und die unteren 12 bit auf 0 gesetzt.
    Addiert man mit \verb|addi| (add immediate) den Inhalt der unteren 12 Bit hinzu, kann man das Register mit den gewünschten 32 Bit füllen.
    Verknüpft man \verb|addi| mit dem Register zero (Register, das immer 0 enthält) als einen Wert, kann das Register sicher mit einer Konstante geladen werden.
    Auch wird hier mit Memory-Mapping gearbeitet, also mit Speicheradressen, die eine bestimmte Funktionalität erfüllen.
    Im Abschnitt \verb|_start:| wird die Basisadresse des GPIO-Registers in \verb|a0| gespeichert.
    Durch das Memory-Mapping bestimmen Werte, die an diese Adresse geschrieben werden, den Zustand des GPIO-Ausgangs.
    Anschließend wird der Wert des Registers \verb|t0| auf 1 gesetzt.
    Im darauffolgenden Abschnitt \verb|loop:| wird der Wert von \verb|t0| mittels der \verb|sb| (store byte)-Instruktion an die zuvor gespeicherte Adresse in \verb|a0| geschrieben.
    Der Zugriff auf die Speicheradresse erfolgt mit \verb|0(a0)|, damit nicht die Speicheradresse selber, sondern das Byte an der Speicheradresse überschrieben wird.
    Danach wird das niedrigste Bit in \verb|t0| durch die \verb|xori| (exclusive OR immediate)-Instruktion invertiert.
    Ist der Wert vorher 1, wird er 0, war er vorher 0, wird er 1.
    Der restliche Code beschreibt die Berechnung von Collatz-Folgen, deren Logik ausführlicher im \cref{collatz-erklärung} (\("\)Methodologie\("\)) erklärt werden.
    Mittels der Pseudoinstruktion \verb|li| (load immediate) \parencite{riscv-pseudoinstructions} werden Register mit festen Werten geladen.
    Dies wird hier genutzt, um eine for-Schleife von 1 bis 1000 zu realisieren.
    \verb|mv| (move) kopiert den Inhalt eines Registers in ein anderes, mit \verb|j| (jump) wird zu einem Label bzw. einer Programmadresse gesprungen.
    Durch den Abschnitt unter \verb|ungerade:| wird eine Berechnung umgesetzt, die eine Multiplikation beinhaltet, ohne das RISC-V Modul zur Ganzzahlmultiplikation miteinzubinden.
    Mit \verb|slli| (shift logical left immediate) in Kombination mit \verb|add| wird die Zahl verdreifacht, da sie zunächst durch eine Verschiebung um eine Stelle nach links verdoppelt und anschließend noch einmal der Ursprungswert addiert wird.
    Anschließend wird durch \verb|addi| der Wert um eins erhöht, sodass \verb|n = 3n+1| aus der Collatz-Folge realisiert wird.
    Im folgenden Abschnitt \verb|check_even_odd:| wird eine Modulo-Operation mit dem Wert 2 zur Überprüfung, ob eine Zahl gerade oder ungerade ist, umgesetzt.
    Dies erfolgt durch die Instruktion \verb|andi| (AND immediate), das Ergebnis der Verundung mit dem Wert 1 wird im Register \verb|a1| gespeichert.
    Hierbei wird ausgenutzt, dass ungerade Zahlen im Binärsystem an letzter Stelle immer eine 1 haben.
    Im Register \verb|a1| kann demzufolge nur eine 0 stehen, wenn die aktuelle Zahl in der Berechnung eine gerade Zahl war.
    Dementsprechend wird mit \verb|bnez| (branch not equal zero) geprüft, ob im Register \verb|a1| eine 0 enthalten ist.
    Ist dies nicht der Fall, war die Zahl ungerade und es wird zum Label \verb|ungerade:| gesprungen.
    Ansonsten war die Zahl gerade und es wird die nächste Instruktion \verb|srai| (shift right arithmetic immediate) ausgeführt, bei der eine Verschiebung um eine Stelle nach rechts \verb|n = n/2| aus der Collatz-Folge umsetzt.
    Der letzte Abschnitt \verb|check_loop_zu_Ende:| überprüft durch Nutztung der \verb|bne| (branch not equal)-Instruktion, ob der Wert 1 erreicht wurde.
    Ist der Wert noch nicht 1, läuft die Collatz-Folge weiter, ansonsten wird mit den Instruktionen \verb|addi| und \verb|bne| der Zähler der for-Schleife inkrementiert sowie die Abbruchbedingung geprüft.
    Ist die Abbruchbedingung (i=1001) noch nicht erreicht, läuft eine Collatz-Folgenberechnung mit neuem Startwert, ansonsten wird zu \verb|loop:| gesprungen, wieder das GPIO-Register beschrieben, \verb|t0| invertiert und die Collatz-Folgenberechnung wieder bei 1 gestartet.

    Ein CPU-Kern, der diese Instruktionen verarbeiten kann ist SERV, ein von Olof Kindgren entwickelter open-source RISC-V CPU-Kern \parencite{kindgren_serv}.
    Dieser setzt die RISC-V ISA im Gegensatz zu anderen Prozessoren bit-seriell um, verarbeitet also pro Takt nur ein Bit statt ganzer 32-Bit-Wörter.
    Somit ist SERV langsamer als andere RISC-V CPUs, erweitert allerdings die Idee der RISC-V-Architektur, weniger Hardwareressourcen zu nutzen, da für die Synthese eines SERV-Kerns deutlich weniger Logikblöcke verwendet werden müssen als für RISC-V CPUs, die vollständige Wörter verarbeiten.
    Dadurch ist SERV einer der kleinsten RISC-V CPU-Kerne und eignet sich besonders für ressourcenkritische Bereiche und Forschungsanwendungen.
    Ein weiterer Vorteil von SERV besteht in der ausführlichen Dokumentation des Projektes, sodass die Replizierbarkeit erleichtert wird, was für wissenschaftliche Fragestellungen besonders relevant ist.
    Im folgenden Code-Ausschnitt der \verb|serv_alu.v| Verilog-Datei wird die bit-serielle Arbeitsweise noch einmal verdeutlicht.

    \begin{minted}[breaklines, fontsize=\small]{verilog}
        (...)
        wire [B:0] add_b = i_op_b ^ {W{i_sub}};
        assign {add_cy, result_add} = i_rs1 + add_b + add_cy_r;
        (...)
        always @(posedge clk) begin
            add_cy_r    <= {W{1'b0}};
            add_cy_r[0] <= i_en ? add_cy : i_sub;
            (...)
        end
    \end{minted}
    \captionof{listing}[Ausschnitt aus serv_alu.v]{Ausschnitt aus der serv_alu.v Verilog-Datei des SERV CPU-Kerns. Die eingefügten (...) zeigen Auslassungen an. Die Verilog-Datei in voller Länge sowie alle anderen zugehörigen Verilog-Dateien sind im SERV GitHub-Repository \parencite{kindgren_serv} zu finden.}
    \label{lst:serv_alu.v}

    Für das Verständnis des Codes ist zu beachten, dass \verb|i_op_b|, \verb|i_sub|, \verb|i_rs1| und \verb|i_en| 1-Bit-Input-Wires sind, die aus anderen Bestandteilen des SERV CPU-Kerns gefahren werden.
    Außerdem ist \verb|W| konstant 1 und es gilt \verb|B = W - 1 = 0|, sodass \verb|add_b| ebenfalls zu einem 1-Bit-Wire wird und sich die erste Zeile des Ausschnitts zu \verb|add_b = i_op_b ^ i_sub| verkürzt (\verb|^| entspricht XOR).
    Dadurch kann das Wire \verb|add_b| sowohl für Addition als auch Subtraktion im Zweierkomplement genutzt werden.
    \verb|i_sub| kontrolliert hierbei, ob addiert oder subtrahiert wird.
    Wird addiert (\verb|i_sub == 0|), gilt \verb|add_b = i_op_b|, wird subtrahiert (\verb|i_sub == 1|), invertiert sich der Wert von \verb|i_op_b| und es gilt \verb|add_b = ~i_op_b|, was später zur Subtraktion im Zweierkomplement (\verb|A - B = A + ~B + 1|) genutzt werden kann.
    In der nächsten Zeile erfolgt die tatsächliche Berechnung.
    Das Ergebnis wird in ein Carry-Bit \verb|add_cy| sowie ein Ergebnis-Bit \verb|result_add| geschrieben.
    Es werden drei 1-Bit-Werte addiert, sodass Werte zwischen 0\textsubscript{10} = 00\textsubscript{2} und 3\textsubscript{10} = 11\textsubscript{2} erreicht werden können, weshalb das Carry- und das Ergebnis-Bit konkateniert werden.
    \verb|i_rs1| ist das nächste zu verrechnende Bit des ersten Operanten, \verb|add_b| ist der je nach Rechenoperation veränderte Wert des zweiten Operanten und \verb|add_cy_r| ist das Carry-Bit aus der vorherigen Berechnung.
    Das Carry-Bit aus der vorherigen Berechnung ist entweder ein klassisches Carry-in aus der im letzten Takt erfolgten Addition, oder aber ein modifiziertes Carry, um die Berechnung der Subtraktion im Zweierkomplement zu starten.
    Im always-Block wird nämlich das Carry-Bit für die nächste Berechnung \verb|add_cy_r| vorbereitet.
    Es wird zunächst auf 0 gesetzt und anschließend überschrieben.
    Das Überschreiben wird durch das Enable-Signal \verb|i_en| gesteuert.
    Ist \verb|i_en == 0| bedeutet dies, dass eine neue Berechnung startet.
    In diesem Fall wird der Wert von \verb|i_sub| in das Carry-Bit für den nächsten Takt geschrieben.
    Soll subtrahiert werden, ist \verb|i_sub| wie oben beschrieben 1 und durch das Setzen des Carry-Bits wird im nächsten Takt die Berechnung von \verb|A + ~B + 1| (Subtraktion im Zweierkomplement) gestartet.
    Soll addiert werden, ist \verb|i_sub == 0|, es existiert noch kein Carry und es wird die Berechnung von \verb|A + B| für die folgenden Takte angestoßen.
    Gilt wiederum \verb|i_en == 1|, ist also das enable-Bit gesetzt, wird aktuell noch gerechnet.
    In diesem Fall wird immer das aktuelle Carry-Bit in den nächsten Takt weitergereicht.
    In diesem Ausschnitt wird das minimalistische, bit-serielle Design von SERV deutlich, da die Berechnung von sowohl Addition als auch Subtraktion mithilfe eines einzigen 1-Bit-Volladdierers über mehrere Takte, also bitweise realisiert wird und dementsprechend zwar langsamer ist, aber mit deutlich weniger Hardware auskommt.

    Servant erweitert den SERV-Kern durch möglichst wenig Peripherie zu einem vollständigen System on a Chip (SoC). So wird der CPU-Kern durch Arbeitsspeicher, Timer und einen GPIO-Pin ergänzt.
    Auch hier wird auf Sparsamkeit bei der Nutzung von Hardwareressourcen gesetzt.
    Dies resultiert in einer minimalistischen Hardwareplattform, auf der z.B. das Zephyr-Betriebssystem, oder andere Software ausgeführt werden kann, weshalb Servant als das SoC gewählt wurde, welches in der vorliegenden Arbeit auf dem Artix-7 FPGA synthetisiert wurde.

\section{Verilator, FuseSoC und Zephyr}
    Bei Verilator handelt es sich um einen zyklus-akkuraten Simulator für Verilog-Code.
    Verilator übersetzt den RTL-Code in C++-Code, welcher zusätzlich in weiteren C++-Code gewrappt werden kann und die Simulation des Hardwaredesigns darstellt.
    Hierbei wird durch die Übersetzung eine sehr schnelle Simulationsgeschwindigkeit erreicht, die deutlich schneller als die zyklus-akkurate Simulation in Vivado - und oft auch schneller als andere vergleichbare Simulatoren ist.
    Während bei der Simulation in Vivado innerhalb mehrerer Minuten nur wenige Millisekunden simuliert werden können, kann bei Verilator der erwartete Programmverlauf nachvollzogen werden, welcher bei Vivado mehrere Stunden bis Tage in Anspruch nehmen würde.
    Ein weiterer Unterschied besteht darin, dass Verilator standardmäßig ein two-state Simulationsmodell nutzt, also dass Leitungen und Register lediglich die Zustände \("\)low\("\) bzw. 0 und \("\)high\("\) bzw. 1 annehmen können.
    In den meisten Fällen ist eine two-state Simulation ausreichend und bietet Vorteile einer höheren Speichereffizienz sowie Geschwindigkeit.
    Die Vivado-Simulation nutzt ein four-state Modell und kennt zusätzlich die Zustände \("\)unknown value\("\) bzw. X sowie \("\)high impedance (hochohmig)\("\) bzw. Z, ist dadurch genauer und eignet sich besser zum Debugging.
    Andere Simulatoren, wie bspw. QEMU \parencite{bellard2005qemu} oder FLASH \parencite{choi2020flash} sind zwar noch schneller als Verilator, jedoch wird der Geschwindigkeitszugewinn hierbei dadurch eine höhere Abstraktionsebene erreicht.
    QEMU ist im Gegensatz zu Verilator eine high-level Simulation, bei der kein RTL-Code simuliert wird, sondern die ISA eines Prozessors, weshalb QEMU sich nicht dazu eignet, die Korrektheit eines Hardwaredesigns zu prüfen.
    Aus diesem Grund wurde Verilator als schnellste verfügbare Simulation auf dem RTL genutzt, um Performanceunterschiede zwischen Simulation und FPGA zu untersuchen.

    Um dies umzusetzen, wurde zusätzlich das open-source Buildtool für Hardwareprojekte FuseSoC \parencite{kindgren_fusesoc} verwendet.
    FuseSoC organisiert Abhängigkeiten und kann durch die Einbindung von Verilator bspw. einen SERV-Kern mit einem Zephyr-Betriebssystem simulieren.
    Zephyr ist hierbei das genutzte open-source real-time operating system (RTOS), welches im Bereich der eingebetteten Systeme Verbreitung findet \parencite{zephyr}.
    Durch sein minimalistisches Design kann Zephyr auch auf kleinen RISC-V Prozessoren laufen.
    Das west-Tool verwaltet im Kontext von Zephyr Projekte und deren Abhängigkeiten und fasst den Bau von Projekten unter einer einzelnen Kommandozeile zusammen.
    Als Alternative zur Nutzung von Zephyr und west existiert die gnu-Toolchain mit Unterstützung von RISC-V Prozessoren \parencite{risc-buildtool}, womit die Software ohne ein entsprechendes Betriebssystem direkt auf der Hardware laufen kann (\("\)bare metal\("\)).
