\section{FPGAs}
    Field Programmable Gate Arrays, oder FPGAs sind beliebig konfigurierbare Hardwareschaltungen.
    Im Gegensatz zu Microcontrollern oder CPUs, bei denen mit festgelegten Instruktionen gearbeitet und Software geschrieben wird, die mit diesen vorgegebenen "Werkzeugen" eine bestimmte Funktion umsetzen, wird bei FPGAs "Hardware entwickelt".
    Hierbei wird mit einer Hardwarebeschreibungssprache eine Schaltung konfiguriert.
    Somit kann Hardware "entwickelt" werden, die einen bestimmten Zweck erfüllt und eine bessere Passung zur gewünschten Funktionalität bietet, als dies z.B. generische Microcontroller tun.
    Derselbe FPGA kann sich je nach Konfiguration bspw. wie eine ALU, ein Microcontroller, eine ARM-CPU oder eine x86-CPU verhalten.

    FPGAs bestehen aus mehreren Logikblöcken, wobei die Anzahl der Logikblöcke die Komplexität an umsetzbaren Schaltungen bestimmt.
    Je mehr Logikblöcke, desto komplexere Schaltungen können mit einem FPGA umgesetzt werden.
    Ein solcher Logikblock enthält Input/Output-Elemente zur Kommunikation (bspw. LEDs, UART), Switching/Routing-Blöcke zur Verbindung der Bauteile sowie sog. Konfiguraitons-Logikblöcke.
    Diese Konfigurations-Logikblöcke generieren aus einem Input-, einem Clock- und einem Resetsignal einen Output durch die Verwendung von Lookup-Tables, Flipflops und Multiplexern.
    %Müssen LUTs, Flipflops und Multiplexer noch mal erklärt werden?
    Durch diese Bestandteile wird dann das gewünschte Verhalten modelliert.
    So kann z.B. jede logische Schaltung, die deterministisch bzw. nicht zeitabhängig ist, in einer Lookup-Table abgebildet werden.
    Für zeitabhängige Schaltungen werden zusätzlich Flipflops und Speicherbausteine genutzt.

    Um zum Punkt einer fertig konfigurierten Hardwareschaltung zu gelangen, wird ein Designprozess durchlaufen.
    Zunächst wird in einer Hardwarebeschreibungssprache Code auf dem Register-Transfer-Level (RTL-Code) geschrieben.
    Die am weitesten verbreiteten Hardwarebeschreibungssprachen sind Verilog und VHDL.
    Dieser RTL-Code kann in einem Analyse- bzw. Simulationsschritt einer ersten Prüfung unterzogen werden, wo grobe Fehler auffallen sollten.
    Im Anschluss erfolgt der Syntheseschritt, indem der RTL-Code in eine Netzliste überführt wird.
    Diese bildet ab, welche Bauteile theoretisch benötigt würden, um die Schaltung wie beschrieben umzusetzen. %Analogie zu Zwischencode beim Kompilieren von Code?
    Im Implementierungsschritt werden in einem sog. Place \& Route-Verfahren die theoretischen Bauteile auf die tatsächlich auf dem FPGA vorhandenen Bauteile gemappt.
    Hier werden benötigte physische Bauteile, also Lookup-Tables, Flipflops und Multiplexer des FPGA verortet und benötigte Bauteile miteinander verbunden. % Ist verortet richtig?
    Diese Informationen werden in einen Bitstream geschrieben.
    In einem letzten Schritt wird dieser Bitstream auf den FPGA übertragen.
    Dies erfolgt entweder persistent in den Flash-Speicher, sodass die Konfiguration bei Neustart des FPGA erhalten bleibt, oder flüchtig in den SRAM.

    Somit bieten FPGAs eine große Flexibilität, da sie jede erdenkliche Schaltung abbilden können und in ihren Funktionen nicht so stark eingeschränkt sind wie z.B. Microcontroller.
    Dadurch können sie auf den jeweiligen Usecase zugeschnitten werden und bieten deshalb meist eine höhere Geschwindigkeit und Energieeffizienz als Microcontroller, weisen gleichzeitig aber auch eine im Vergleich größere Komplexität auf.

\subsection{Basys 3-Board}
    Beim Basys 3-Board handelt es sich um ein FPGA-Board mit Artix-7 FPGA und einiger Peripherie für den universitären Kontext, welches auf das initiale Befassen mit FPGAs ausgelegt ist. \todo{Foto des FPGA einbinden?}
    Das Board besteht aus dem FPGA selber, Kommunikationschips für USB/serielle-Kommunikation, verschiedenen Buttons und Schaltern, einer 7-Segment-Anzeige, LEDs, einem VGA-Ausgang und USB-Port sowie aus Anschlüssen für Erweiterungen.
    Normalerweise setzen FPGA-Boards auf general purpose Input/Output (GPIO) Pins, um nach Wunsch verschiedenste Peripherie nutzen zu können und haben eher selten diesen Umfang an Knöpfen, Schaltern, Anzeigen und eingeschränkten Anschlüssen.
    Für die vorliegende Arbeit wurden lediglich der FPGA selber sowie eine fest installierte LED und ein Button verwendet.
    Das Basys 3-Board verfügt über eine 100MHz Clock, welche voll ausgenutzt wurde, ca. 33.000 Logikblöcke mit etwa 310.000 Lookup-Tables, von denen nur ein kleiner Anteil genutzt wurde sowie 1800Kbit RAM.

\subsection{Vivado}
    Ähnlich wie bei der Entwicklung von Software, gibt es auch für den Hardwareentwicklungsprozess Entwicklungsumbgebungen (IDEs).
    Vivado ist hierbei eine weit verbreitete, kommerzielle IDE vom Hersteller AMD, mit welcher der gesamte Entwicklungsprozess durchlaufen werden kann.
    So bietet die IDE Funktionalitäten zum Schreiben und Organisieren von RTL-Code, zur zyklus-akkuraten Simulation von Schaltungen, zur Umsetzung der Synthese- und Implementierungsschritte sowie zur Generierung des Bitstreams und der Übertragung auf den FPGA.

\section{RISC-V/SERV}
    RISC-V ist eine open-source Instruction Set Architecture (ISA), die die "Sprache" des Prozessors festlegt. RISC-V CPUs sind solche, die diese Prozessorinstruktionen verarbeiten können.
    SERV ist eine sehr kleine open-source bit-serielle (1 bit pro Takt) RISC-V CPU.
    Servant ist ein System on Chip (SoC), welches die SERV-CPU mit minimaler Peripherie (Timer, Speicher, 1-bit GPIO-Pin) erweitert, um das Zephyr-Betriebssystem auf der CPU laufen lassen zu können.
    Servant ist am Ende auch das SoC, welches auf dem Artix-7 FPGA synthetisiert wurde.

\section{Verilator}
    Simulator für Verilog-Code: Übersetzt den RTL-Code in ein eigenes, schnelles Verilog-Modell, das dann in C++-Code gewrappt wird und simuliert somit die
    Erreicht durch diesen Zwischenschritt eine sehr schnelle Simulation (und ist mindestens gleich schnell, oft schneller als andere Simulatoren)
    Unterschied zu anderen Simulationen: low-level, gleichzeitig sehr schnell
    Verilator wird wiederum mit fusesoc genutzt, um serv-RTL-Code zu simulieren und ist das zugrundeliegende Tool für die im Rahmen der Bachelorarbeit durchgeführten Simulationen

\section{Zephyr}
    Open-source Real-Time Operating System (RTOS) für FPGAs, sehr basic, sodass es auch auf kleine RISC-V Prozessoren läuft
    Quasi Softwareplattform für FPGAs/Microcontroller
    Alternative zu Zephyr: Buildtooling von SERV --> "bare metal"

\section{fusesoc}
    Open-source Buildtool für Hardwareprojekte, organisiert bspw. Abhängigkeiten und kann bspw. Simulation eines SERV-Kerns umsetzen und Zephyr einbinden
